# 山易排盘架构评估与演进方案

评估日期：2026-09-08。代码基线：`9a1ac69`。线上抽查：`http://43.134.64.51:8002/`。

本次为架构分析，没有修改业务代码或线上配置。依据为源码、构建配置、本地古籍数据、自动化检查及公网 HTTP 响应；未执行完整浏览器交互测试、容量压测、数据库审计或命理专家校验。

## 结论

网站已经有较完整的产品功能，但架构仍以浏览器本地应用为中心。最需要投入的地方是统一计算口径、可追溯报告、可靠内容更新和真实账号服务。建议沿现有 React/Vite 逐步重构，采用模块化单体后端，保留游客本地计算与知识库离线阅读。

现有可保留的基础：`lunar-javascript` 历法依赖、`core/types.ts` 类型定义、本地古籍分篇、账号加密存储、排盘回归样例、GitHub 自动检查与 Nginx 静态部署。

### 1. 公网 HTTP 与账号实现不匹配

证据：`src/auth.ts:118` 在没有 `crypto.subtle` 时直接抛错；`src/main.tsx:12` 注册 Service Worker；`deploy/server/docker-compose.yml` 映射 `8002:80`。本次公网根路径返回 200，未跳转到 HTTPS。

Web Crypto 的 `subtle` 和 Service Worker 依赖安全上下文。因此在普通默认浏览器里，当前公网 HTTP 入口无法按预期支持这些能力。本次依据代码、响应和浏览器规范得出，未冒充浏览器实测登录结论。

处理：将 HTTPS 公共入口作为账号正式使用的前置条件；8002 可继续作为源站端口。域名暂缓时可先采用有效的临时 HTTPS 入口。切换协议或域名会改变浏览器存储来源，必须提供用户主动导出、导入的迁移路径，不能默认老账号自动出现。

资料：[MDN Crypto.subtle](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/subtle)、[MDN Service Worker](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API)。

### 2. 排盘规则需要一个统一入口

证据：`src/core/bazi.ts:376` 和 `src/App.tsx:781` 都有十二长生计算；组件文件还包含十神、神煞、起卦、岁运和调候分析。`ReadingPort` 当前返回同步结果，`RemoteReadingService` 只是抛错占位（`src/adapters/readingService.ts:10`）。

已确认的具体问题：

- `src/App.tsx:338` 将节气日期写死，专业细盘用这些日期构造流月和流日范围。用项目已有历法库复算，2025 年清明为 4 月 4 日 20:48:36，而固定表为 4 月 5 日；2026 年芒种为 6 月 5 日 23:48:21，而固定表为 6 月 6 日。组件应使用逐年节气时刻并明确时区、交节日的展示口径。
- `src/core/bazi.ts:280` 在时辰未知时用正午占位；`createBaziReading` 仍计算全部四柱并将时柱计入五行、旺衰与详批。提示文字不足以表达下游结论的不确定性。
- `getDayMasterStrength` 依赖同党分数阈值，`getUsefulElements` 主要依据日主五行与强弱三档选取。四家方法解读复用了这些指标，不能把四段文案视为四套独立校验结果。
- `createMethodSynthesis` 的“较高”置信度由相同强弱阈值决定，没有经过外部标注案例校准。应表述为规则证据完整度，避免展示成已验证的预测准确度。

处理：统一输出历法事实、干支关系、规则判断和证据，由页面负责展示。未知时辰使用空值或候选时柱集合，并在每条判断上保留依赖字段和不确定性。规则适用条件、例外和争议都应进入数据模型。

### 3. 档案需要区分原始输入、历史报告和最新重算

证据：`src/operations.ts:64` 保存出生输入、四柱和版本，没有完整报告快照；`src/App.tsx:4961` 打开档案调用 `generateReading`。`core/bazi.ts` 多处直接读取当前年份。

影响：同一档案在规则升级或跨年后，旧报告内容可能变化。即使记录了旧版本号，也无法恢复旧详批。档案保存还按姓名、日期、时间合并，未将性别、地点与校正口径纳入区分，同名同时间的不同方案可能被覆盖。

处理：

- `BirthProfile` 保存出生资料及修订记录。
- `ReadingSnapshot` 保存本次完整结果、生成时间、分析基准日期和全部版本号。
- 用户主动“按最新规则重算”时新增快照，保留旧报告。
- 用明确档案 ID 和修订 ID 标识记录，不以姓名与出生时间代替唯一标识。
- 把当前时间作为 `AnalysisContext.asOf` 传入；相同输入、上下文和规则版本得到相同分析结果。

### 4. 前端按功能拆分，建立真实路由

证据：`src/App.tsx:4757` 使用 `step` 控制登录、首页、录入、报告、起卦和学堂；学堂一个组件承载课程、题库、古籍请求、缓存和多个选择状态。页面切换不写入 URL。

影响：无法直接定位某篇古籍或报告页；刷新、浏览器后退与页面内返回不一致；后续 App 深链接也没有稳定目标。功能代码虽有动态导入，但页面主体仍在同一个入口文件。

建议路由：`/home`、`/birth`、`/reports/:id`、`/yijing`、`/learn`、`/classics/:bookId/:chapterId`。私有报告 ID 不意味着公开授权；路由恢复必须等待账户解锁或会话校验。

先抽出学堂、起卦、出生录入和报告四个功能目录。每个目录管理自己的组件、状态和局部样式；共享层只保留真正复用的表格、弹窗、导航和主题变量。分离浏览器存储、日期与网络适配器，核心计算不依赖 React 或 DOM。

本次构建的入口 JS 为 406.50 kB（构建估算 gzip 127.90 kB），全站 CSS 为 90.40 kB（gzip 16.90 kB）；按需载入的繁简转换字典块为 1,181.70 kB（gzip 515.26 kB）。后者不是每次首屏都加载，应先拆分功能页面和样式，再按实际调用评估字典范围。构建给出的 gzip 数字不代表线上已经启用压缩，也不代表实测首屏耗时。

### 5. 古籍更新链路存在确定的缓存与响应问题

证据：`src/App.tsx:3030` 将章节存入 `localStorage`；目录与章节请求均使用 `force-cache`。`scripts/split-classics.mjs:9` 的版本是“日期 + 段落数”，文件 URL 未包含内容版本。`public/sw.js` 对同源 GET 统一网络优先，失败后统一回退到页面 HTML。

影响：同一天纠正文句但段落数不变，版本号不变，已有本机章节缓存会被直接复用。不同缓存层也缺少共同的失效标准。普通 HTTP 的 8002 入口下 Service Worker 通常不生效，其回退问题主要影响 HTTPS/PWA 入口。

本次实测不存在的 `/knowledge/classics/does-not-exist.json` 返回 `200 text/html`，说明线上 Nginx 把数据路径也当作 SPA 页面回退；客户端会遇到 JSON 解析失败。103,396 字节的卷十 JSON 在请求接受 gzip 时没有返回 `Content-Encoding`，至少这次响应未启用压缩。

处理：

- 目录短缓存并重新验证；章节采用内容哈希 URL 和不可变缓存。
- 公共古籍正文放 Cache Storage 或 IndexedDB；localStorage 只放少量偏好。公共书籍缓存与私有加密档案分别管理空间和错误。
- 缓存仅保留应用自己的命名空间；页面导航才能回退 HTML，JSON 缺失必须返回真实错误。
- Service Worker 按导航、静态资源、古籍和将来的私有 API 分策略，默认不缓存私有 API。
- 支持书籍离线下载、占用空间展示、版本检查、删除下载以及容量不足后的正常在线阅读。

### 6. 知识库需要从文件集合升级为可引用的内容库

本地六书共 180 篇/卷，但“目录数正确、段落非空、没有 Wiki 标记”的检查不能证明底本完整或文字准确。

数据核验：六书共有 9,200 个正文块；128 个非空 `commentary` 全在《滴天髓》，界面将其标为“底本旧注”。其余五书此字段为空。每篇有导读，但 `ClassicTextBlock` 没有独立的现代译文、译者、审核状态或稳定段落 ID。部分源注保留在原文字段内，不能仅用 `commentary` 计数判断是否有注释。

报告中的书名、原句和解读由代码内常量及规则拼装，没有通过本地正文块 ID 关联。增加古籍文件不会自动使详批引用更丰富或更精确。

建议关系：`Book -> Edition -> Chapter -> Passage -> Annotation/Translation`。段落需要稳定 ID；版本变化时保存旧 ID 映射，保护书签和历史引用。译文应有作者或生成来源、审核状态和版本，不能把篇章导读当作全文翻译。

每条报告判断关联 `ruleId`、输入事实、适用条件、反证条件以及 `editionId/passageId`；用户可从结论跳到原文上下文。规则推导与原文摘录分别记录。

内容生产流程：抓取原始响应并存档 -> 解析成段落/表格等结构 -> 校验缺卷、空文、异常缩短和重复 -> 生成与上一版的差异 -> 校订 -> 发布版本清单。现有正则清洗可继续处理简单段落，但有表格、嵌套模板时需要结构化解析并保留原始材料。

课程与古籍搜索分别建索引；现有书内搜索只匹配标题和导读，不是全文检索。第一阶段可以构建本地分书全文索引，正文结果直接定位段落，无需立即引入独立搜索服务。

### 7. 正式账号采用单后端与数据库，本地模式继续保留

现有 PBKDF2 和 AES-GCM 能为本机档案提供加密隔离，但账号注册、验证、档案和学习记录都在同一浏览器。换设备、清理站点数据和忘记密码没有服务端恢复途径。

建议先建设一个后端服务，集中承担认证、档案、学习进度和反馈，配一个关系数据库。选择与当前 TypeScript 团队能力相符的实现即可；无当前流量证据支持引入微服务、Kubernetes 或多种数据库。

服务端以会话确定用户身份，每次读取/修改都验证记录归属；Web 采用安全 Cookie 会话。未来 App 使用专门的凭据存储适配器。游客数据继续本地计算，用户明确选择迁移哪些本机档案后再上传。

离线同步采用稳定记录 ID、记录修订号、待同步队列、幂等请求和删除标记。冲突不能直接覆盖；报告快照不可变可降低冲突复杂度。需要同时交付导入、导出及备份恢复验证。

另一个边界问题：登录将完整 `StoredAccount` 赋给 session，`getActiveAccount()` 仅展开对象；TypeScript 的返回类型不会在运行时删掉 salt/verifier 等字段，数据导出可能携带本机凭据验证材料。应以白名单映射公开资料。此项不等同于发现明文密码泄漏。

本机仓库整包加密并排队写入，尚无跨标签页冲突控制；学习进度等调用多处不等待写入结果。应统一保存状态和失败通知，再为账号仓库补充修订检查与跨标签页协调。

### 8. 交付与测试需要覆盖用户真正经过的路径

仓库有 GitHub Pages 自动检查与发布，未发现面向 8002 的版本化自动发布工作流。本次未审计服务器上的其他运维工具，因此不能断言服务器完全没有外部监控或备份。

建议统一构建、测试、制品版本与发布清单。GitHub Pages 可明确作为预览入口；正式入口单独配置，版本应能查询和回滚。Nginx 镜像版本固定，发布后检查根页、真实章节、缺失章节、注册/登录路径和上一版本回滚。

现有反馈与事件接口可配置，但错误只写本机，代码不能证明运营方已接收到反馈。建议接入反馈状态、匿名错误上报和关键路径可用性监控，并在服务器发布流程中实际验证。

本次 16 项测试已通过。它们覆盖基础四柱、校正、本机加密隔离、知识库结构等，但没有覆盖浏览器路由、HTTP 安全上下文、缓存升级、布局和网络失败。详批测试的“不完全相等”及文本长度检查，也不能证明内容推理正确或重复率足够低。

优先增加：节气前后一刻/跨年/月末/不同换日口径；未知时辰依赖传播；同输入同版本复现；跨账号越权；真实浏览器注册和退出；快速切书竞态；断网、缓存满、旧版升级；移动端导航和年月日选择。

## 二、目标结构

```text
Web / 后续 App
  页面：排盘、报告、起卦、学堂、账号
    应用服务：生成报告、保存档案、读取古籍、同步进度
      领域核心：历法事实、干支关系、规则评估、证据与解读、起卦
      适配器：本地存储、远程 API、时钟、内容仓库

统一后端：认证、档案、报告快照、学习进度、反馈
  关系数据库：用户及私有业务记录
  版本化静态内容：原文、译注、课程、检索索引

离线内容流水线：抓取 -> 解析 -> 校验 -> 校订 -> 版本发布
```

`ReadingPort` 应改为异步契约，并支持取消与结构化错误；本地、Worker 和远程实现共享返回结构。先测量计算耗时，只有在长任务影响交互时才移入 Worker。大文件体积本身不能证明需要计算服务集群。

规则结果建议包含：`ruleId`、`ruleVersion`、`inputFacts`、`evidenceRefs`、`counterEvidence`、`uncertainty`。分别记录历法版本、规则版本、内容版本和译注版本，避免一个日期版本号覆盖所有变化。

## 三、实施顺序与验收

| 阶段 | 具体任务 | 完成标准 |
| --- | --- | --- |
| 1. 纠正可靠性问题 | HTTPS 入口方案；真实节气；未知时辰；JSON 404；内容哈希缓存 | 正常浏览器登录可用；节气边界有样例；未知信息不产生确定结论；新版章节不读旧缓存 |
| 2. 拆分现有代码 | 功能目录、真实路由、统一规则、存储/时钟适配器 | 页面无业务计算；刷新与后退可恢复路径；现有正常案例无非预期变化 |
| 3. 报告与内容版本 | 快照、版本上下文、段落 ID、引用关联、译注模型 | 旧报告可复现；结论可定位原文；原文修订不丢书签；导读和译文有明确区分 |
| 4. 运营后端 | 认证、数据库、档案/学习同步、反馈、迁移 | 跨设备一致；账号隔离；冲突可处理；迁移和备份恢复经过验证 |
| 5. 发布与性能 | 8002 发布流水线、监控、分包、压缩、离线下载、全文搜索 | 自动检查与回滚可运行；页面实际传输与交互指标有前后对比 |

每一阶段均应形成可独立发布、可回滚的变更。第一轮建议将范围限定在阶段 1 和规则抽离，随后用报告快照稳定数据契约，再建设账号同步。

工期需在确认账号恢复方式、旧数据迁移规模、支持的出生年份/地区与译文审核资源后估算；本次没有根据流量或团队配置编造吞吐量和工期承诺。
